# ADR-0019: 用 collectedAt 記錄收藏事件，不由狀態反推

Date: 2026-08-27 | Status: accepted

## Context

`words.status` 同時承載兩件事：`unknown` 代表「已收藏的生詞」，`known` 代表「我認得，別再標」。
按 `X` 排除一個從未收藏的字時，`markWord` 會建出一列 `createdAt` 是當天的資料，
學習足跡於是把「排除」顯示成「新收藏」，愈排除愈多。

改用 `status === 'unknown'` 過濾能讓症狀消失，卻會弄壞對稱的案例：收藏後標成「已馴服」的字，
整段歷史會從原本那天消失。另一個方向也錯：先按 `X`、日後才收藏時，`markWord` 保留最初的 `createdAt`，
收藏會被記到按 `X` 那天。單一欄位無法同時表達「現在是什麼」與「何時收藏」。

## Decision

- `words` 新增 `collectedAt`。`markWord` 轉成 `unknown` 時寫入現在時間，其餘狀態保留原值，`X` 排除維持 `null`。
- 學習足跡的「新收藏」只看 `collectedAt`，不再看 `status`。
- 同步時 `collectedAt` 不交給 ADR-0009 的 `updatedAt` last-write-wins 決定，改取兩邊非空值中較晚的一個；
  結果不等於遠端時標成 pending 補推。
- 舊資料由 `inferCollectedAt` 推斷一次：目前是生詞、留過語境或練習過就視為收藏過，其餘視為排除。
  同一套規則也在 `schema.sql` 回填雲端，否則全新裝置只會拉到一片空白的歷史。

## Alternatives

- **用目前的 `status` 反推**：最省事，但修好「按 X」就弄壞「已馴服」，兩個方向只能二選一。
- **用 `contexts` 最早的日期推導**：不必加欄位，但 `addContext` 對單字有 26 字元下限，
  收藏過的字可能一條語境都沒有，月曆會漏掉它們。
- **把「排除」拆成獨立資料表**：模型更乾淨，收藏與排除本來就是兩件事，
  但要新增一張同步表並搬遷既有 `known` 列，而且仍需另一個旗標保住「已馴服」統計。
- **回填時一併更新 `updatedAt`**：一行就能避免拉取覆蓋，但會讓沒有語意變更的列贏過
  別台裝置較新的改動，例如對方昨天標成已馴服會被本機過期的 `status` 蓋掉。

## Consequences

學習足跡不再隨狀態變化改寫歷史，收藏日與「現在是不是生詞」完全脫鉤。

`collectedAt` 是第一個不遵守 ADR-0009 last-write-wins 的欄位。回填刻意不動 `updatedAt`，
因此它必須搭配「取較晚值」的合併規則才安全，兩者是一組，不能只留其中一個。
之後若再加類似的衍生欄位，要一併想清楚合併規則。

「先按 `X`、日後才收藏」的舊資料會被算在按 `X` 那天。真正的收藏日從來沒有被記錄過，救不回來。

本 ADR 取代 ADR-0015 中「新收藏依 `words.createdAt`」的部分。
