# ADR-0029: 輸出契約給填好的範例，解析端容忍已知偏差

Date: 2026-09-01 | Status: accepted

## Context

`SYSTEM_RULES.lookup` 原本用欄位說明描述三選一那兩行：`選項｜干擾項A｜干擾項B｜干擾項C`
與 `答案｜正確選項是第幾個(1-3)`。真實模型把說明當成要填寫的內容，回出
`答案｜正確選項是第1個`，並把 `選項｜` 字首當成欄位名而整個省略。

`extractQuiz` 兩個條件都不成立，依照「寧可不出題」的設計回 `null`，
於是這個功能在真實模型下從未出現過。`stripQuiz` 只認有字首的選項行，
所以那兩行還原樣印在卡片頂端，答案在作答之前就被看到。

348 個 unit test 全過，因為它們餵的都是格式正確的字串。契約的另一端是模型時，
mock 的輸入永遠是自己想像中的輸入。

## Decision

規格改成一個填好的範例，加一句「`答案｜` 後面只寫 1、2 或 3 這一個數字」。
解析端同時接受兩種已觀察到的偏差：答案行取第一個 1–3 的數字；
選項行沒有 `選項｜` 字首時，由下一行的 `答案｜` 當錨點認出來。
`stripQuiz` 與 `extractQuiz` 共用同一個形狀判斷。

## Alternatives

- **只改 prompt**：沒有真實模型的測試環境，等於賭一把。換模型或換 `baseUrl` 會再遇到同一件事。
- **只放寬解析**：模型的格式變異沒有上限，一種一種追不完，而且會愈放愈鬆。
- **改用 JSON 或 structured outputs**：查詞是串流的，選項必須跟第一批 token 一起到才有意義；
  JSON 要等整份收完才能 parse，「先猜」省下的等待就沒了。而且不是每個相容端點都支援。
- **解析失敗就自動重問一次**：一次失敗要多花一次完整查詢的錢，
  而且這種偏差是系統性的，同一個 prompt 重問很可能再錯一次。

## Consequences

字首變成可選之後，理論上任何「三段 ｜ 分隔、而且下一行是答案行」的開頭都會被當成題目。
實務上正文第一行是 `## 本句用法`，切不出三段，所以誤判空間很小。
守住的不變式從「選項行有字首」換成「答案行是錨點」。

代價是壞題偵測變難：以前格式錯就完全沒有題目，很明顯；現在可能出一題內容半對的。
真正的防線因此落在 `quizLog` 的答對率上，不在解析器。
